# 매장 생산·할인·매출 통합 지침

## 적용과 기본 동작

사용자가 매장의 생산량, 저울 누계, 할인, 폐기, 매출 또는 일일 실적을 물으면 이 지침으로 관련 자료를 연결한다. `월계 생산량이랑 매출`, `어제 왕십리 실적`, `오늘 저울누계 할인까지` 같은 표현을 처리한다.

- 매장은 명시된 매장, 없으면 현재 대화에서 확정된 매장을 사용한다. 날짜는 명시된 날짜, 없으면 한국시간 오늘이다. 어제는 요청 당시 한국시간 전날로 해석한다.
- 매장이 불명확하면 매장만 질문한다. 다른 매장이나 이전 영업일의 실적·행사를 자동으로 가져오지 않는다.
- 좁은 질문에는 요청한 항목을 우선 답한다. 생산·매출 종합 요청에는 생산수량, 생산금액, 할인, 전환·폐기, 할인후생산금액, 실제 매출과 차이를 함께 보여준다.
- 조회 요청은 읽기 전용이다. 사용자의 생산·부착·폐기·정정 발언은 해당 날짜 운영기록에 저장한다. 커밋·푸시는 요청받았을 때만 한다.

## 원본과 역할

- 시코드 `products_{store}`: 현재 운영상품·앱 가격. [매장·상품 지침](STORE_PRODUCTS_GUIDE.md)을 따른다.
- CASPi CL-5200 X1: 저울 품목별 누계금액·중량·수량·라벨 수. 생산실적의 관측 근거이며 결제 매출을 증명하지 않는다.
- 시코드 `print_records_{store}`, `v_discount_records`: 할인 출력 근거. 실제 부착은 사용자 확인과 연결한다.
- 사용자 현장보고: 원물 투입, 추가생산, 포장수량, 부착, 재사용·전환, 폐기, 출력 오류의 근거.
- 실제 매출: [매출 진입점](../../instances/sales/README.md)과 [공통 매출 지침](SALES_COMMON_GUIDE.md)에 따라 검증된 Supabase 자료를 조회한다. 월계는 [대영](DAEYOUNG_SALES_GUIDE.md), 마포·미아·왕십리는 [남선](NAMSEON_SALES_GUIDE.md)이다.
- 원물·레시피·원가는 [레시피·원가 지침](RECIPES_COST_GUIDE.md), 기록은 [공통 데이터 지침](DATA_RULES_GUIDE.md)을 따른다.

## CASPi 누계 조회 경로와 날짜

CASPi는 우리 `cascl5200` 프로젝트의 매장 라즈베리파이 저울 프로그램이다. 별도 웹사이트나 열린 앱 창을 찾는 것으로 조회를 끝내지 않는다.

- 프로젝트: `C:\Users\tlseo\OneDrive\문서\cascl5200`
- 읽을 문서: 해당 프로젝트 `AGENTS.md`, `CASPI_ARCHITECTURE.md`, `scale-data/PLU_AGGREGATE_COLLECTION.md`
- 중앙 원본 DB: `%LOCALAPPDATA%\CAS-CL5200\aggregate-central\aggregate-central.sqlite3`
- 수집 회차: `imported_collection`, 원시 누계: `imported_plu_snapshot`, 증가분: `plu_delta`
- 매장 대응: `wolgye → wolgye2`, `mapo → mapo2`, `mia → mia2`, `wangsimni → wangsim2`
- 중앙 DB는 SQLite 읽기 전용 연결로 조회한다. 자격증명은 설정된 환경변수만 사용하고 출력하지 않는다.

1. 한국시간 영업일의 `[00:00, 다음 날 00:00)`을 UTC로 변환하여 시작과 종료 조건을 모두 적용한다. 과거 날짜 조회에 종료 조건을 빠뜨리지 않는다.
2. 해당 매장의 최신 수집시각, 당일 회차 수, 첫·마지막 회차, 직전 기준선과 수집 공백·초기화·NULL 증가분을 확인한다. 첫 회차 증가분이 전날까지 걸치거나 긴 공백이 있으면 당일분 확정에 한계를 표시한다.
3. 검증된 증가분을 합산한다. 누계 스냅샷 여러 회차를 단순 합산하지 않는다. 초기화는 기존 수집기의 기준선 규칙을 따르고 음수 매출로 만들지 않는다.
4. `최신` 요청마다 다시 조회한다. 최신 DB 시각이 이전과 같으면 그대로 알린다. DB 조회시각을 저울 수집시각처럼 말하지 않는다.
5. 데이터가 오래됐으면 기존 동기화 상태·로그와 허용된 읽기 전용 Pi 내보내기 경로를 점검한다. 조회를 위해 저울 초기화, 설정 변경, 서비스 재배포를 하지 않는다.
6. 작업용 PLU는 프로젝트의 검증된 매장별 제외 설정과 최신 용도를 확인하여 별도로 표시한다. 모든 매장에 같은 번호를 적용하지 않는다. 원본은 보존한다.

## 상품 연결과 생산량

- 매장·부서·PLU·상품코드와 앱 `mart_code`로 연결한다. 이름만으로 다른 상품을 합치지 않는다. PLU 이름·가격의 스냅샷 시각도 확인한다.
- `팩`은 기본적으로 원물 투입, `개`는 완제품이다. `300g씩 8팩 포장`처럼 완제품을 명시하면 그 뜻을 우선한다. [생산량 지침](PRODUCTION_GUIDE.md)을 따른다.
- 원물 팩당 중량·박스 구성·포장중량·수율은 날짜별로 기록한다. 중간 투입량을 최종 투입량으로 고정하지 않는다. 추가·정정·현재 총량을 구분하고 기존 신고와 근거를 보존한다.
- 신고 생산량과 저울 관측값을 별도 보관한다. 생산 중에는 이후 누계 증가가 추가 생산일 수 있다. 라벨 수만으로 실제 포장 완료를 무조건 확정하지 않는다.
- 저울 `수량`과 `라벨 수`를 함께 확인한다. 보통 한 장당 한 상품이지만, 수량 7을 한 장에 출력한 경우처럼 다를 수 있다. 차이는 현장 확인 후 해석한다.
- 월계는 할인 라벨을 시코드에서 별도 출력한다. 시코드 할인 재출력을 저울 누계에서 임의 차감하지 않는다. 저울 자체의 재출력·오출력은 별도 확인한다.
- 월계 큰새우살의 500g 고정상품과 일반 중량상품은 사용자 확인에 따라 합산한다. 확인된 PLU 17·25 연결은 해당 날짜 코드·용도를 재확인하고 적용한다. 500g은 표시중량 환산이며 실측중량과 구분한다. 다른 새우 PLU는 자동 합산하지 않는다.
- 중량상품은 수량 필드가 0이어도 라벨 수·중량을 제시한다. 생산금액은 검증된 라벨 누계금액을 사용하고 고정상품·중량상품의 단가를 구분한다.
- 용지 소진 시 누계가 증가하는지는 검증 없이 단정하지 않는다. 사용자의 일반 질문을 실제 사고 발생으로 기록하지 않는다. 포함 여부가 불명확하면 `누계 반영 미확인`으로 표시하며, 최소값이라고 단정하거나 미출력 수량을 자동 가산하지 않는다.

## 할인 연결과 중복 방지

1. 매장·영업일 범위를 고정하고 모든 페이지를 조회한다. 취소 `is_void`를 집계에서 제외하되 원본은 지우지 않는다.
2. 출력수·실제 부착수·사전 출력·오출력을 구분한다. 사용자 `붙였어` 확인은 해당 묶음에 적용하고, 전날의 40% 사전 출력 규칙을 오늘로 자동 이월하지 않는다.
3. 출력 ID, 시각, 상품 식별자, 할인율, 수량, 원가가 아닌 정상 판매금액, 할인액, 최종가격, 원본·출력 바코드, 단계 정보를 함께 본다.
4. 같은 물건의 재할인만 이전 단계를 대체한다. 중량 가격 바코드는 개별 상품 고유번호가 아니므로 동일 바코드만으로 확정 연결하지 않는다. 출력 수량을 보존하고 가능한 연결 수를 넘겨 매칭하지 않는다.
5. 문어탕 20% 15장과 30% 15장처럼 연결이 불명확한 출력은 별도 상품인지 재할인인지 확인한다. 단계값 1만으로 신규 상품이라고 확정하지 않는다.
6. 최종 할인상품 수가 생산·이월재고와 맞는지 검산한다. 초과하거나 연결이 모호하면 확정액 대신 근거 있는 추정·범위 또는 조건부 계산을 제시한다. 단순 출력 할인액 합계를 최종 할인액으로 쓰지 않는다.
7. 당일 생산에 귀속되는 최종 부착 할인만 할인후생산금액에 반영한다. 이월상품·날짜 불명 상품의 할인은 분리한다.
8. 금액은 앱 기록의 정상가·최종가 차이와 수량을 확인한다. 표시 할인율만 곱해서 앱의 원 단위 처리를 덮어쓰지 않는다.

## 전환·폐기·금액 정의

- `생산금액`: 당일 생산분의 정상 판매가 기준 금액. 생산 시점부터 적용한 특가는 해당 날짜의 기준가로 구분 기록한다.
- `조정 생산금액`: 생산금액에서 다른 완제품으로 전환되어 중복된 원상품 금액을 뺀 값. 완성된 대상 상품이 누계에 이미 포함됐는지 확인한다.
- 전환은 폐기와 다르다. 원상품·대상상품·수량·중량·가격·시각을 연결한다. `약 5팩`을 정확한 값으로 저장하지 않는다. 실제 팩별 중량이 없으면 비례추정 근거를 표시한다.
- `할인후생산금액 = 조정 생산금액 − 당일 생산분 최종 적용 할인액`
- 폐기는 별도 수량·금액으로 표시한다. 이미 할인된 상품은 할인후 금액 기준 폐기가액을 사용하여 중복 차감을 피한다. 필요하면 `폐기 차감 후 상품금액`을 추가하되 실제 매출로 부르지 않는다.
- `실제 매출`: 검증된 매출 원본의 판매금액. 생산금액·출력금액·할인후생산금액과 구별한다.
- 월계 대영매출은 사용자 확인 기준 이마트 수수료 21.5% 차감 후 금액이다. 비교할 때 `차감 전 환산 매출 = 대영매출 ÷ 0.785`로 복원한다. 21.5%를 단순 가산하지 않는다. 해당 자료의 기준 변경 여부를 확인하고 다른 매장에는 자동 적용하지 않는다.
- 생산과 매출은 같은 매장·기간·수수료·세금·상품 범위에서 비교한다. 이월재고, 폐기, 전환, 미판매분, 수집 공백이 있으면 차이를 설명하며 단순 차액을 재고손실이나 이익으로 단정하지 않는다.
- 조회되지 않는 값은 `미확인`으로 표시한다. 없다는 이유로 0원이나 전날 값으로 대체하지 않는다.

## 저장과 마감

- 운영 요약: `instances/operations/{store}/YYYY-MM.yaml`. 월계 일일 ID는 `ops_wg_YYYYMMDD`이며 같은 영업일 레코드는 하나다.
- 원물 신고, 저울 관측값, 실제 확인 수량, 추정 수량, 전환, 할인 부착, 폐기, 실제 매출을 구별한다. 시각·원본 식별자·계산 근거·미확정 사유를 함께 남긴다.
- 중간 생산 신고를 저울 수량으로 덮어쓰지 않는다. 갱신이 필요하면 이전 신고와 수정 근거를 메모 또는 이력으로 보존한다.
- CASPi 원시 DB·프레임·대량 누계, 시코드 원시 출력 전체는 운영 YAML에 복제하지 않는다. CAS 프로젝트에는 실제 누계 DB를 커밋하지 않는다. Waterbe에는 필요한 날짜별 요약과 현장 정정만 보관한다.
- 기록 수량·품목 합계·금액 식을 검산하고 YAML을 파싱한다. 모호한 바코드 연결이나 추정 전환금액이 남으면 `finalized: false`를 유지한다.
- 다음 날 잔여라벨·재고·폐기 확인은 [월계 일일 운영 지침](../../WOLGYE_DAILY_OPERATIONS_GUIDE.md)을 함께 따른다. 잔여라벨로 판매를 역산할 때 분실·오출력·재고이월 등 가정이 충족됐는지 확인한다.

## 휴대폰 답변 형식

넓은 표 대신 짧은 목록을 사용한다. 매장·날짜와 저울·할인·매출 각각의 기준시각을 표시한다. 원물 기준은 필요할 때만 덧붙이고 같은 상품의 포장규격은 합계와 세부를 연결한다.

```text
월계 · 9월 25일
저울 20:22 / 할인 18:37 / 매출 집계일 …

문어탕 15개 · 생산금액 357,000원
→ 35% 할인 7개 · 할인액 58,310원

큰새우살 총 ○개 · ○kg
→ 500g ○개 + 일반포장 ○개

생산금액 …원
전환 조정 …원
최종 부착 할인액 …원
할인후생산금액 …원
폐기 …개 · …원
실제 매출 …원 (수수료 기준)
비교 차이 …원

확인 필요: …
```

`할인 적용하면 얼마?`에는 계산 가능한 할인후생산금액을 첫 문장에 답하고 추정·부착 조건을 바로 붙인다. 확인되지 않은 연결을 확정했다고 말하지 않는다.
