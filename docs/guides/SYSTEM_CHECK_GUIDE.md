# 여기서 전체 시스템 점검

사용자가 '전체 점검', '수파/중앙/라즈 확인'을 요청하면 이 입구를 사용한다.
실행 위치와 점검 창구는 다르다. 중앙 워커는 씽크패드에서만 실행하지만,
이 명령은 현재 Windows 워터비 세션에서 전체 점검을 시작한다.

```powershell
python scripts/waterbe_api.py call system.check
```

## 경로와 범위

- 수파: 현재 호스트 Supabase CLI의 기존 로그인으로 직접 프로젝트 상태와
  제한된 읽기 전용 DB 통계(연결/활성쿼리/대기잠금/최장 활성시간/DB크기)를 조회한다.
  ThinkPad를 거쳐 수파를 조회하지 않는다. CLI 위치는 PATH 또는 기존 설치 경로,
  명시한 WATERBE_SUPABASE_CLI를 쓴다. 자동 로그인/키 탐색/인증 복사는 하지 않는다.
- 중앙: 공통 ssh thinkpad로 기존 manage check와 현재 operations.db를 읽는다.
  워커 상태·최근 실행·출처 확인시각·대기/격리·실패 분류를 합친다.
- 매장: 씽크패드의 기존 매장 SSH 별칭으로 등록된 5개 CASPi 서비스 및 누계 DB
  관측 상태를 읽는다. 저울 명령/신규 누계 수집/쓰기/네트워크 설정 변경은 없다.
- 점검 코드는 정확한 현재 버전을 SSH 표준입력으로 실행한다.
  원격 파일 설치/워커 교체/재시작/DB 작성/예약 작업 추가가 아니다.

## 답변 기준

`available`은 증거 조회 성공이지 전체 정상 판정이 아니다. `partial`이면 실패한
경로와 reason을 그대로 표시하고 다른 경로의 결과를 버리지 않는다.
명령 timeout/권한 부족을 수파 장애로 단정하지 않는다. 오래된 관측의 available도
현재 정상으로 바꾸지 않는다. checked_at과 자료 age/freshness를 함께 본다.
중앙 source 관측은 20분 초과 시 stale로 표시하며 업무별 최신성은 해당 지침으로
추가 판단한다. DB 파일 수정시각은 실제 저울 수집 성공시각을 대신하지 않는다.
CASPi 저장 관측은 3분 초과 시 stale로 표시한다. 이는 최근성 경고이며
장비 고장/생산 없음/실패 재시도 정책 위반의 확정이 아니다.
관리 ACTIVE_HEALTHY는 앱 REST 전체 성공이나 휴대폰 전환 성공이 아니다.

사용자에게 영향 → 확인된 상태/시각 → 미확인 범위 → 필요한 조치 순서로 보고한다.
무가공 CLI 출력·SSH 오류·환경변수·인증·SQL 본문은 출력하지 않는다.
재시작/복구는 점검과 분리하고 담당 가이드와 승인 범위를 따른다.

## 준비와 한계

이 호스트의 기존 Supabase CLI 로그인, ssh thinkpad 키 접속 및 씽크패드 매장 접속이
필요하다. 다른 컴퓨터도 코드는 재사용하지만 호스트별 인증은 별도 준비한다.
휴대폰 설치/화면/Bluetooth, 물리 저울 읽기·쓰기, 수파 I/O 예산·CPU·RAM,
모든 앱 snapshot 필드 검사는 자동 확인 범위 밖이다. 이번 명령이 모든 업무 기능의
정상을 보장하거나 장애를 무인 복구하지 않는다.
