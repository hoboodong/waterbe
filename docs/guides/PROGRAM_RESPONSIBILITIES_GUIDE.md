# 워터비 프로그램 구성·역할 지침

기준일: 2026-10-01 (사용자 업무 중심 단순화 기준 추가)

워터비 사업에 필요한 프로그램을 여섯 역할로 구분한다. 이 문서는 담당 프로젝트와 책임의 기준이며, 프로그램 존재와 실제 배포·정상 가동을 구별한다. 새 코덱스도 프로젝트 간 업무를 시작하기 전에 이 구분을 따른다.

## 기본 원칙

- 워터비는 사업 운영과 통합 조회를 주관한다. 시코드와 카스씨엘을 대신 구현하는 프로젝트가 아니다.
- 시코드는 현장 앱과 앱 원본, 카스씨엘은 저울 통신·수집·검증, 워터비는 사업 계산·현장정보 통합·보고를 책임진다.
- 같은 접속·수집·계산 기능을 여러 프로젝트에 중복 구현하지 않는다.
- 코드가 있다는 것, 배포됐다는 것, 현재 정상이라는 것은 다르다. 현재 가동·자료시각·권한은 실제 점검 후에만 확정한다.
- 아래 미구현 기능을 기존 기능처럼 안내하거나 호출하지 않는다. 완성 전 조회는 [통합 운영 조회 지침](DAILY_STORE_REPORT_GUIDE.md)을 따른다.

## 에이전트 공통 API 진입점

기능 목록의 기준은 [API 카탈로그](../../config/api_catalog.json), 공통 실행 입구는
`python scripts/waterbe_api.py`다. HTTP 서버를 새로 배포한 것이 아니라 기존 API를
찾고 안전한 조회 어댑터를 호출하는 Python/CLI 입구다.

1. `python scripts/waterbe_api.py list`로 업무 ID·담당·원본·부작용·구현 상태를 확인한다.
2. `python scripts/waterbe_api.py describe sales.daeyoung.read`처럼 해당 항목을 확인하고
   그 항목의 `guide` 문서를 반드시 읽는다.
3. `state=gateway`만 공통 `call`로 실행한다. `native`는 기존 담당 프로젝트의
   검증된 입구를 사용하며 공통 어댑터 연결 전 상태다. `planned`는 호출하지 않는다.
4. 조회와 변경·수집·동기화를 구별한다. 목록 발견이나 조회 요청이 쓰기 승인이 되지 않는다.

현재 공통 호출 가능 기능은 남선·대영의 날짜별 **매출 원본 조회**다.
예: `python scripts/waterbe_api.py call sales.daeyoung.read --date 2026-10-01`.
실행 호스트 환경변수 `SUPABASE_URL`(HTTPS), `SUPABASE_SERVICE_ROLE_KEY`가 필요하다.
키를 지침·Git·대화에 기록하지 않는다. 자동 `.env` 탐색이나 다른 프로젝트 키 복사는 하지 않는다.
어댑터는 GET만 사용하고 전체 페이지·원본 행수·원본 버전 일치를 확인한다.
남선 월누계, 대영 검증상태·수수료, 매장명 연결은 매출 지침에 따라 별도 해석한다.

결과의 `fetched_at`은 조회시각이지 자료 최신시각이 아니다. `data.sources`의
날짜·수정/적재시각·검증상태를 함께 확인한다. `available`도 최신 동기화나
통합 계산 완료를 뜻하지 않는다. `missing_source`는 조회한 저장소에 원본이 없다는
뜻일 뿐, 실제 매출 0을 뜻하지 않는다. `unavailable`, `unsupported`,
`invalid_request`는 실패/미지원이며 금액으로 바꾸지 않는다.

저울 누계·상품·할인·변경·동기화는 기존 입구를 목록에 연결했지만 공통 호출 어댑터는
아직 미연결이다. 생산·할인·폐기·매출 종합 계산과 재고·레시피·인사 API는 미구현이다.
후속 구현은 카탈로그의 해당 항목과 어댑터·테스트를 같이 갱신하고, 실제 원본 검증 및
호스트 설치를 확인한 뒤에만 사용 가능 상태로 올린다. 이 목록만으로 전 매장 배포를 주장하지 않는다.

## 사용자 업무 중심 단순화 — 2026-10-01 합의

원칙은 **업무는 밖으로, 처리 과정은 안으로**다. 아래는 목표 설계이며,
문서 기록만으로 기존 앱·워커·자동 동기화가 변경되거나 완성된 것은 아니다.

- 사용자 입구는 앱과 대화다. 매장·날짜를 정하고 생산·할인·폐기·매출 등을
  조회하거나 입력·수정한다. API·CLI·워커·작업 ID를 알아야 사용할 수 있게 하지 않는다.
- GUI·CLI·API는 각각 별도 업무 시스템이 아니라 같은 기능의 입구다.
  같은 업무의 계산·검증·저장 규칙을 공통 기능으로 모으고, CLI는 운영·진단용으로 둔다.
- 연결 경로 선택, 자료 수집, 동기화, 중복 방지, 검증, 안전한 재시도,
  중단된 작업 재확인과 잠금 관리는 내부 처리다. 결과가 불명확한 저울 쓰기는
  자동 재전송하지 않는다. 사용자에게는 필요한 행동만 안내한다.
- 결과는 수량·금액·업무 날짜·자료 기준시각·처리 상태를 중심으로 보여준다.
  휴대폰 저장, 저울 실제 반영, 서버 반영을 구별하며 단순히 모두 ‘완료’로 표시하지 않는다.
  연결 실패나 자료 미확인을 ‘0’ 또는 ‘기록 없음’으로 대신하지 않는다.
- 매출 수집·동기화·중복 및 합계 검증도 내부화한다. 사용자는 매출과 마지막 반영 시각,
  최신 자료 여부를 보고, 필요할 때만 새로고침한다. 조회 요청이 기존의 삭제·정리·업로드를
  포함하는 일괄 동기화 스크립트 실행 권한이 되는 것은 아니다. 조회 전용 경로와
  승인된 수집·적재 경로를 분리한 뒤 연결한다.
- 시코드는 현장 입력·원본, 카스씨엘/CASPi는 저울 실행·검증, 워터비는 사업 계산·보고를
  맡는다. 앱 상품·저울 설정·저울 출력금액·실제 매출은 다른 자료이므로 합쳐 덮지 않는다.

정리 순서는 기존 기능 목록과 실제 실행 주체 확인 → 공통 요청·결과 형식 →
각 입구 연결 → 내부 자동 처리 → 검증·설치·배포다. 기능별로 담당, 원본,
호출 경로, 결과 저장 위치, 실제 적용 상태와 남은 작업을 확인한다.
중복처럼 보이는 파일도 사용 여부를 검증하기 전 삭제하지 않는다.

## 데이터 워커 구성 — 출처별 관리

목적은 불완전한 현장기록도 제대로 축적·정제하여 생산 운영 개선에 사용하는 것이다.
입력은 유연하게 받되 원본·정제·보정·분석 결과는 구별한다. 매장마다 워커를 만들지 않는다.
구성의 기계 판독 기준은 [데이터 워커 목록](../../config/data_workers.json)이다.
이 파일은 설계 등록이며 실행·설치·자동화 완료를 뜻하지 않는다.

| 워커 ID | 담당 | 데이터 범위 |
| --- | --- | --- |
| raspi_data | 카스씨엘 | 모든 라즈의 누계·수집 상태·실행 증거 |
| seacode_discounts | 시코드 | 모든 매장의 할인 출력·취소·부착 확인 |
| namseon_sales | 워터비 | 남선 일매출·월누계·원본 버전 |
| daeyoung_sales | 워터비 | 대영 이미지·판독·합계 검증·수수료 기준 |
| integrated_data | 워터비 | 출처 간 상품 연결·보정·통합 집계·분석용 이력 |

기존 저울 수집기와 매출 적재기는 재사용한다. 출처별 정제 규칙은 담당 프로젝트가
관리하고, 공통 기록 계약·교차 출처 연결·분석 기준은 워터비가 관리한다.
워커는 논리적인 책임 구분이며 반드시 각각 별도 프로세스를 띄운다는 뜻은 아니다.
매장·장비·상품은 데이터 속성과 연결 정보로 관리한다. 순회 라즈는 장비 ID와
방문 기간을 보존해 수집 당시 매장에 연결하며 현재 위치로 과거 기록을 바꾸지 않는다.

### 제대로 쌓기 위한 공통 계약

- 원본: 출처·원본 ID·버전·내용 해시·수집시각·원문 또는 보존 위치를 필수로 저장한다.
  발생시각·매장·상품이 없으면 누락 사유를 남겨 수집하고 추후 연결한다. 임의 값을 채우지 않는다.
- 정제: 원본 ID, 정제 규칙 버전, 상품 연결 버전과 품질 표식을 남긴다.
- 보정: 대상·근거·작성자·기록시각·이전 보정과의 관계를 별도로 남긴다.
- 분석: 사용한 원본/보정·계산 버전·기준시각·신뢰도를 남겨 재현 가능하게 한다.

같은 원본·같은 버전의 재수집은 중복 가산하지 않는다. 수정된 원본은 새 버전으로
남긴다. 원본 보존 후에만 수집 진행 위치를 전진시키고, 정제 결과와 처리 위치는
트랜잭션 또는 재실행 안전한 전달 큐로 일관되게 반영한다.
늦게 들어온 원본·보정은 해당 매장/날짜/상품 범위만 다시 계산한다.

잘못된 레코드는 격리·보존하고 나머지 처리는 계속한다. 확정·추정·미확인을 구별하고
추정에는 근거를 붙인다. 할인 출력=부착, 누계금액=매출, 생산-매출=폐기로 단정하지 않는다.
새 자료 도착 시 처리하고 정기 누락 점검을 보완한다. 실제 주기·호스트는 배포 때 정한다.
데이터 수집 재시도는 저울 쓰기 재전송 권한이 아니며 불확실한 쓰기는 기존 재확인 절차를 따른다.

상태 조회에는 처리 위치·원본 기준시각·마지막 성공시각·대기/격리 건수·오류를 제공한다.
공통 워커 상태/재처리/보정 API는 아직 미구현이며 API 목록의 기존 조회 기능과 혼동하지 않는다.

구현 순서는 공통 저장 계약 → 출처별 어댑터·정제 → 통합 연결·재계산 → 분석이다.
검증은 출처별 대표 사례로 하며 매장별 복제 개발은 하지 않는다. 완료 조건은 재수집 중복 방지,
원본 수정·늦은 도착·중단 후 재개·보정 재계산·불량 레코드 격리·결과 근거 추적을 통과하는 것이다.

## 1. 시코드 — 현장 앱

- 사장님 UI 전담 세션은 시코드 `AGENTS.md`의 새 세션 역할 확인을 거쳐
  시코드 `docs/UI_COLLABORATION_GUIDE.md`를 따른다. 전체 기능 세션과 작업 공간을
  분리하되 공용 배포는 사용자 요청 시 같은 통합·검증·배포 규칙으로 수행할 수 있다.
  이 워터비 역할 지침은 UI 규칙을 복제하지 않는다. 현재 로컬 시코드 저장소는
  `D:/dev/seacode_new`이며 다른 호스트에서는 해당 저장소의 실제 위치를 확인한다.

- 담당 프로젝트: `seacode_new`.
- 상태: 기존 프로그램. 생산량 화면은 CASPi Bluetooth가 연결되지 않았을 때 Supabase 중앙 요청 경로로 읽기 전용 누계를 조회할 수 있다. 앱 설치 버전과 매장별 연결 상태는 별도 확인한다.
- 책임: 매장별 운영상품·앱 가격·운영상태, 상품/할인 라벨 출력, 출력·취소 상태, 앱 생산 입력, 상품↔PLU 연결과 현장 화면.
- 제공 자료: 상품·가격·연결 상태, 할인 원본, 앱에서 입력한 생산·폐기 원본.
- 경계: 출력한 라벨은 실제 부착·판매의 증거가 아니다. 인쇄 작업 한 행과 라벨 장수를 구별한다. 사업 종합 계산을 앱에서 따로 복제하지 않는다.
- 실제 연결 등록·변경은 시코드의 기존 binding 기능이 담당하며, 워터비는 소비·대조한다.

## 2. CASPi 및 기존 매장 수집기 — 매장 저울 담당

- 담당 프로젝트: `cascl5200`.
- 상태: 기존 프로그램·수집 경로 있음. 매장별 V1/V2 전환과 활성 실행 주체는 별도 확인한다.
- 책임: 매장 저울 정보·누계 읽기, 원본 보관, 허용된 저울 명령 실행과 결과 검증.
- 제공 자료: PLU·상품코드·원시 카운터·수집 회차·검증 결과.
- 경계: CASPi는 Supabase 자격증명을 보유하거나 직접 연결하지 않는다. 운영 집계와 실제 매출 판정을 맡지 않는다.
- 기존 타이머와 CASPi를 확인 없이 병설하지 않는다. 매장별 저울 접근·쓰기 실행 주체와 잠금은 카스씨엘의 기존 아키텍처를 따른다.

## 3. 카스씨엘 중앙 프로그램 — 매장 연결·저울 데이터 제공

- 담당 프로젝트: `cascl5200`. CASPi와 같은 프로젝트의 다른 실행 부분이다.
- 상태: 기존 동기화·게시·장비 관리 기능 있음. 시코드의 CASPi 미연결 생산 누계 요청을 처리하는 중앙 읽기 워커가 배포되어 있다. 워터비 통합 보고용 표준 기간 조회는 별도 보완이 필요하다.
- 책임: 매장별 접속·인증, 누계 가져오기·보관·게시, 저울 변경 요청 처리·백업·검증, 수집 품질 진단.
- 새 제공 기능: 지정 기간의 검증된 증가분, 직전 기준선, 초기화·공백·게시 완결 여부를 포함한 읽기 전용 조회.
- 경계: 최신 누계 합계를 당일 생산량으로 대신하지 않는다. 접속 방법을 워터비 에이전트가 매번 탐색하도록 넘기지 않는다.
- 기존 `aggregate_sales_report.py`는 최신 누계 요약이며, 필요한 날짜별 통합 조회가 이미 완성됐다는 근거가 아니다.
- 중앙 읽기 대체 경로는 `collect_aggregate`와 `aggregate_day`만 허용한다. 저울 쓰기 대체 경로나 워터비 전체 매출·할인 통합 조회가 완성됐다는 뜻이 아니다.

## 4. 매출 수집·검증 프로그램 — 실제 매출 담당

- 담당 프로젝트: `waterbe`.
- 상태: 기존 코드·업무 지침 있음. 스케줄 실행과 최신 데이터 반영 여부는 별도 확인한다.
- 남선: 매출표 수집 → SQLite 검증 → Supabase 적재·조회.
  - `scripts/namseon_sales.py`
  - `scripts/namseon_drive_sync.py`
  - `scripts/namseon_supabase_sync.py`
  - `scripts/namseon_sync_now.sh`
- 대영: 매출 이미지 판독 → 합계 검증 → 검증상태와 함께 적재.
  - `scripts/daeyoung_sales_ocr.py`
  - `scripts/daeyoung_supabase_sync.py`
- 경계: 실제 매출 자료를 담당하며 저울 출력금액과 혼용하지 않는다. 단순 매출 조회를 원본 정리·적재 작업으로 바꾸지 않는다.
- `namseon_sync_now.sh`는 Drive 정리·중복 휴지통 처리·적재·업로드를 포함하는 Linux용 실행기다. 조회 전용 명령이 아니며 동기화 요청 범위에서만 사용한다.
- 상세 기준은 [매출 진입점](../../instances/sales/README.md)을 따른다.

## 5. 워터비 통합 운영 프로그램 — 사업 전체 연결

- 담당 프로젝트: `waterbe`.
- 상태: 기획 / 미구현. 현재 개발 우선순위의 핵심이다.
- 책임: 시코드·카스씨엘·검증 매출·현장정보를 연결해 생산량·생산금액·최종 부착 할인·전환·폐기·실제 매출을 계산하고 보고한다.
- 현장정보: 추가생산·원물 투입·포장수량·부착 확인·오출력·재사용·전환·폐기. 앱 입력과 대화 신고가 같은 생산이면 이중 가산하지 않는다.
- 확장 영역: 레시피·원가·재고·입고·직원 등 워터비 사업정보와의 연결. 이 영역이 모두 자동화됐다는 뜻은 아니다.
- 실행 형태: 처음에는 요청형 조회 명령. 이후 필요할 때만 정기 요약·결과 캐시 워커를 추가하고 계산 코드는 공유한다.
- 경계: 저울 접속·프로토콜을 복제하지 않고, 실제 조회 없이 계획량이나 0으로 채우지 않는다. 조회가 앱·저울 변경을 자동 실행하지 않는다.
- 결과: 같은 원본 버전·현장정보·기준시각·계산 버전에는 같은 수치가 나오는 구조화 결과와 모바일 출력.

## 6. 텔레그램·코덱스 연결 — 질문·답변 창구

- 담당: 기존 텔레그램 연결 프로그램은 메시지 전송, 워터비는 업무 요청 해석·조회 호출·업무 결과 형식을 담당한다.
- 상태: 현재 대화 창구로 사용 중. 새 통합 조회 프로그램 연결과 터미널 출력 분리는 보완 필요.
- 책임: 인증된 사용자의 질문에서 매장·날짜·요청 항목을 전달하고, 조회 결과를 휴대폰용으로 제공한다. 불명확한 현장정보는 확인한다.
- 경계: 코덱스가 접속법·금액 계산을 매번 새로 만들지 않는다. 터미널 진행 화면·SSH 로그·자격증명·계정 사용량은 업무 답변으로 중계하지 않는다.
- 전송부의 실제 저장소·실행 설정은 변경 전에 확인한다. 이 문서만으로 별도 프로젝트의 서비스 수정·재시작을 승인하지 않는다.

## 공통 인프라와 실행 장소

- Supabase: 원본/검증자료의 저장·교환 장소. 저장 위치와 데이터의 업무 소유권은 다르다.
- GitHub: 코드·지침·필요한 운영 요약의 버전 관리. 원시 누계 DB와 자격증명 보관소가 아니다.
- 씽크패드: 워터비 조회와 중앙 기능을 실행할 호스트. 새 통합 프로그램의 초기 실행 장소로 제안한다.
- Windows 중앙 PC 등 기존 호스트: 실제 DB·수집 주체를 확인해 유지하거나 별도 승인된 전환을 진행한다. 씽크패드에 저장소가 있다는 이유로 모든 서비스가 이전됐다고 보지 않는다.

## 남은 구 구현 — 현행 기능으로 사용하지 않음

### 구 발주 계산

- `scripts/calc_order.py`는 `.openclaw/shared/waterbe` 경로와 폐기된 `production/templates/{store}.yaml`의 계획량에 의존한다.
- 옛 계획 파일 제거 후에도 코드가 남아 있다. 현행 자료에 바로 사용할 준비가 된 발주 프로그램이 아니다.
- 계획 템플릿을 복원해 실행하지 않는다. 후속 작업에서 제거하거나 실제 재고·입고·사업 기준을 사용하는 새 설계로 전환한다.

### 구 YAML 동기화

- `scripts/sync_to_supabase.py`: YAML → `github_*` 테이블.
- `scripts/export_github_data.py`: `github_*` 테이블 → GitHub YAML 갱신.
- 현행 시코드 운영상품 조회기가 아니다. 현행 상품 소유권·경로·권한·실제 호출 여부를 검증하기 전 통합 조회에 연결하지 않는다.

### 과거 매출 이관 실행기

- `scripts/daeyoung_full_ocr.ps1`은 2026년 2~8월 대상이 고정된 과거 일괄 처리 코드다.
- 범용 상시 매출 수집 워커로 소개하거나 일일 조회 때 실행하지 않는다.

위 코드는 이번 문서화에서 삭제·변경·실행하지 않았다. 정리 미완료 항목으로 명시하며 후속 변경은 별도로 처리한다.

## 개발·완료 기준

- 개발 순서: 공통 저장 계약 → 라즈·할인·남선·대영 출처별 어댑터·정제 → 통합 연결·재계산 → 분석・사업정보 확장. 2026-10-01 합의로 매장별 개발 대신 출처별 개발을 따른다. 특정 매장은 검증 사례로만 선택하며 별도 워커를 복제하지 않는다.
- 상세 구현안·검증 항목: [통합 운영 조회 기획안](../plans/INTEGRATED_OPERATIONS_QUERY_PLAN.md).
- CASPi 현장 Bluetooth와 휴대폰/Pi 이중 전달, 사건별 증명, 충돌 격리·해제는 [CASPi·시코드 사건 증명 및 무중단 복구 기획안](../plans/CASPI_SEACODE_EVENT_PROOF_PLAN.md)을 따른다.
- 완료는 코드 작성·푸시가 아니라 원본 접근, 상품 연결, 계산 검산, 새 세션 재현, 모바일 결과 전달까지 확인한 상태다.
- 메인 지침에는 이 문서의 연결을 두고, 역할·상태 변경은 이 문서에서 관리한다. 다른 프로젝트의 구현 상태나 공동 계약이 달라지면 관계 문서를 확인한 뒤 갱신한다.
