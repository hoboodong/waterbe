# 워터비 프로그램 구성·역할 지침

기준일: 2026-09-28

워터비 사업에 필요한 프로그램을 여섯 역할로 구분한다. 이 문서는 담당 프로젝트와 책임의 기준이며, 프로그램 존재와 실제 배포·정상 가동을 구별한다. 새 코덱스도 프로젝트 간 업무를 시작하기 전에 이 구분을 따른다.

## 기본 원칙

- 워터비는 사업 운영과 통합 조회를 주관한다. 시코드와 카스씨엘을 대신 구현하는 프로젝트가 아니다.
- 시코드는 현장 앱과 앱 원본, 카스씨엘은 저울 통신·수집·검증, 워터비는 사업 계산·현장정보 통합·보고를 책임진다.
- 같은 접속·수집·계산 기능을 여러 프로젝트에 중복 구현하지 않는다.
- 코드가 있다는 것, 배포됐다는 것, 현재 정상이라는 것은 다르다. 현재 가동·자료시각·권한은 실제 점검 후에만 확정한다.
- 아래 미구현 기능을 기존 기능처럼 안내하거나 호출하지 않는다. 완성 전 조회는 [통합 운영 조회 지침](DAILY_STORE_REPORT_GUIDE.md)을 따른다.

## 1. 시코드 — 현장 앱

- 담당 프로젝트: `seacode_new`.
- 상태: 기존 프로그램. 생산량 화면은 CASPi Bluetooth가 연결되지 않았을 때 Supabase 중앙 요청 경로로 읽기 전용 누계를 조회할 수 있다. 앱 설치 버전과 매장별 연결 상태는 별도 확인한다.
- 책임: 매장별 운영상품·앱 가격·운영상태, 상품/할인 라벨 출력, 출력·취소 상태, 앱 생산 입력, 상품↔PLU 연결과 현장 화면.
- 제공 자료: 상품·가격·연결 상태, 할인 원본, 앱에서 입력한 생산·폐기 원본.
- 경계: 출력한 라벨은 실제 부착·판매의 증거가 아니다. 인쇄 작업 한 행과 라벨 장수를 구별한다. 사업 종합 계산을 앱에서 따로 복제하지 않는다.
- 실제 연결 등록·변경은 시코드의 기존 binding 기능이 담당하며, 워터비는 소비·대조한다.

## 2. CASPi 및 기존 매장 수집기 — 매장 저울 담당

- 담당 프로젝트: `cascl5200`.
- 상태: 기존 프로그램·수집 경로 있음. 매장별 V1/V2 전환과 활성 실행 주체는 별도 확인한다.
- 책임: 매장 저울 정보·누계 읽기, 원본 보관, 허용된 저울 명령 실행과 결과 검증.
- 제공 자료: PLU·상품코드·원시 카운터·수집 회차·검증 결과.
- 경계: CASPi는 Supabase 자격증명을 보유하거나 직접 연결하지 않는다. 운영 집계와 실제 매출 판정을 맡지 않는다.
- 기존 타이머와 CASPi를 확인 없이 병설하지 않는다. 매장별 저울 접근·쓰기 실행 주체와 잠금은 카스씨엘의 기존 아키텍처를 따른다.

## 3. 카스씨엘 중앙 프로그램 — 매장 연결·저울 데이터 제공

- 담당 프로젝트: `cascl5200`. CASPi와 같은 프로젝트의 다른 실행 부분이다.
- 상태: 기존 동기화·게시·장비 관리 기능 있음. 시코드의 CASPi 미연결 생산 누계 요청을 처리하는 중앙 읽기 워커가 배포되어 있다. 워터비 통합 보고용 표준 기간 조회는 별도 보완이 필요하다.
- 책임: 매장별 접속·인증, 누계 가져오기·보관·게시, 저울 변경 요청 처리·백업·검증, 수집 품질 진단.
- 새 제공 기능: 지정 기간의 검증된 증가분, 직전 기준선, 초기화·공백·게시 완결 여부를 포함한 읽기 전용 조회.
- 경계: 최신 누계 합계를 당일 생산량으로 대신하지 않는다. 접속 방법을 워터비 에이전트가 매번 탐색하도록 넘기지 않는다.
- 기존 `aggregate_sales_report.py`는 최신 누계 요약이며, 필요한 날짜별 통합 조회가 이미 완성됐다는 근거가 아니다.
- 중앙 읽기 대체 경로는 `collect_aggregate`와 `aggregate_day`만 허용한다. 저울 쓰기 대체 경로나 워터비 전체 매출·할인 통합 조회가 완성됐다는 뜻이 아니다.

## 4. 매출 수집·검증 프로그램 — 실제 매출 담당

- 담당 프로젝트: `waterbe`.
- 상태: 기존 코드·업무 지침 있음. 스케줄 실행과 최신 데이터 반영 여부는 별도 확인한다.
- 남선: 매출표 수집 → SQLite 검증 → Supabase 적재·조회.
  - `scripts/namseon_sales.py`
  - `scripts/namseon_drive_sync.py`
  - `scripts/namseon_supabase_sync.py`
  - `scripts/namseon_sync_now.sh`
- 대영: 매출 이미지 판독 → 합계 검증 → 검증상태와 함께 적재.
  - `scripts/daeyoung_sales_ocr.py`
  - `scripts/daeyoung_supabase_sync.py`
- 경계: 실제 매출 자료를 담당하며 저울 출력금액과 혼용하지 않는다. 단순 매출 조회를 원본 정리·적재 작업으로 바꾸지 않는다.
- `namseon_sync_now.sh`는 Drive 정리·중복 휴지통 처리·적재·업로드를 포함하는 Linux용 실행기다. 조회 전용 명령이 아니며 동기화 요청 범위에서만 사용한다.
- 상세 기준은 [매출 진입점](../../instances/sales/README.md)을 따른다.

## 5. 워터비 통합 운영 프로그램 — 사업 전체 연결

- 담당 프로젝트: `waterbe`.
- 상태: 기획 / 미구현. 현재 개발 우선순위의 핵심이다.
- 책임: 시코드·카스씨엘·검증 매출·현장정보를 연결해 생산량·생산금액·최종 부착 할인·전환·폐기·실제 매출을 계산하고 보고한다.
- 현장정보: 추가생산·원물 투입·포장수량·부착 확인·오출력·재사용·전환·폐기. 앱 입력과 대화 신고가 같은 생산이면 이중 가산하지 않는다.
- 확장 영역: 레시피·원가·재고·입고·직원 등 워터비 사업정보와의 연결. 이 영역이 모두 자동화됐다는 뜻은 아니다.
- 실행 형태: 처음에는 요청형 조회 명령. 이후 필요할 때만 정기 요약·결과 캐시 워커를 추가하고 계산 코드는 공유한다.
- 경계: 저울 접속·프로토콜을 복제하지 않고, 실제 조회 없이 계획량이나 0으로 채우지 않는다. 조회가 앱·저울 변경을 자동 실행하지 않는다.
- 결과: 같은 원본 버전·현장정보·기준시각·계산 버전에는 같은 수치가 나오는 구조화 결과와 모바일 출력.

## 6. 텔레그램·코덱스 연결 — 질문·답변 창구

- 담당: 기존 텔레그램 연결 프로그램은 메시지 전송, 워터비는 업무 요청 해석·조회 호출·업무 결과 형식을 담당한다.
- 상태: 현재 대화 창구로 사용 중. 새 통합 조회 프로그램 연결과 터미널 출력 분리는 보완 필요.
- 책임: 인증된 사용자의 질문에서 매장·날짜·요청 항목을 전달하고, 조회 결과를 휴대폰용으로 제공한다. 불명확한 현장정보는 확인한다.
- 경계: 코덱스가 접속법·금액 계산을 매번 새로 만들지 않는다. 터미널 진행 화면·SSH 로그·자격증명·계정 사용량은 업무 답변으로 중계하지 않는다.
- 전송부의 실제 저장소·실행 설정은 변경 전에 확인한다. 이 문서만으로 별도 프로젝트의 서비스 수정·재시작을 승인하지 않는다.

## 공통 인프라와 실행 장소

- Supabase: 원본/검증자료의 저장·교환 장소. 저장 위치와 데이터의 업무 소유권은 다르다.
- GitHub: 코드·지침·필요한 운영 요약의 버전 관리. 원시 누계 DB와 자격증명 보관소가 아니다.
- 씽크패드: 워터비 조회와 중앙 기능을 실행할 호스트. 새 통합 프로그램의 초기 실행 장소로 제안한다.
- Windows 중앙 PC 등 기존 호스트: 실제 DB·수집 주체를 확인해 유지하거나 별도 승인된 전환을 진행한다. 씽크패드에 저장소가 있다는 이유로 모든 서비스가 이전됐다고 보지 않는다.

## 남은 구 구현 — 현행 기능으로 사용하지 않음

### 구 발주 계산

- `scripts/calc_order.py`는 `.openclaw/shared/waterbe` 경로와 폐기된 `production/templates/{store}.yaml`의 계획량에 의존한다.
- 옛 계획 파일 제거 후에도 코드가 남아 있다. 현행 자료에 바로 사용할 준비가 된 발주 프로그램이 아니다.
- 계획 템플릿을 복원해 실행하지 않는다. 후속 작업에서 제거하거나 실제 재고·입고·사업 기준을 사용하는 새 설계로 전환한다.

### 구 YAML 동기화

- `scripts/sync_to_supabase.py`: YAML → `github_*` 테이블.
- `scripts/export_github_data.py`: `github_*` 테이블 → GitHub YAML 갱신.
- 현행 시코드 운영상품 조회기가 아니다. 현행 상품 소유권·경로·권한·실제 호출 여부를 검증하기 전 통합 조회에 연결하지 않는다.

### 과거 매출 이관 실행기

- `scripts/daeyoung_full_ocr.ps1`은 2026년 2~8월 대상이 고정된 과거 일괄 처리 코드다.
- 범용 상시 매출 수집 워커로 소개하거나 일일 조회 때 실행하지 않는다.

위 코드는 이번 문서화에서 삭제·변경·실행하지 않았다. 정리 미완료 항목으로 명시하며 후속 변경은 별도로 처리한다.

## 개발·완료 기준

- 개발 순서: 공통 계약·접근 경로 확인 → 월계 생산 조회 → 월계 할인·현장정보 → 실제 매출 및 4개 매장 → 사업정보 확장. 첫 조회 대상은 2026-09-26 사용자 선택으로 월계로 변경했다.
- 상세 구현안·검증 항목: [통합 운영 조회 기획안](../plans/INTEGRATED_OPERATIONS_QUERY_PLAN.md).
- CASPi 현장 Bluetooth와 휴대폰/Pi 이중 전달, 사건별 증명, 충돌 격리·해제는 [CASPi·시코드 사건 증명 및 무중단 복구 기획안](../plans/CASPI_SEACODE_EVENT_PROOF_PLAN.md)을 따른다.
- 완료는 코드 작성·푸시가 아니라 원본 접근, 상품 연결, 계산 검산, 새 세션 재현, 모바일 결과 전달까지 확인한 상태다.
- 메인 지침에는 이 문서의 연결을 두고, 역할·상태 변경은 이 문서에서 관리한다. 다른 프로젝트의 구현 상태나 공동 계약이 달라지면 관계 문서를 확인한 뒤 갱신한다.
