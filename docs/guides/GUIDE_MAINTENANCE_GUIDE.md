# 워터비 지침 관리 기준

## 목적과 문서 계층

채팅 기억 없이 같은 업무를 같은 기준으로 수행하도록 한다.

- `AGENTS.md`: 에이전트 시작 규칙·공통 제한·메인 목차 연결.
- `WATERBE_GUIDE.md`: 분야별 안내와 담당 지침 연결. 세부 규칙을 복사하지 않는다.
- `docs/guides/`: 반복 업무의 기준·원본·실행 순서·완료 조건.
- `docs/plans/`: 기획, 구현 단계, 이전·복구 계획과 검증 기록.
- 업무별 기록 폴더: 실제 실행 결과와 근거. 품질점검은 `docs/quality-compliance/`.
- 시코드·카스씨엘 프로젝트: 각 프로젝트의 코드·빌드·배포·장비 실행 절차 원본.
  워터비는 프로젝트별 책임과 찾아가는 경로를 연결한다.

현재 파일 위치를 임의로 옮기거나 이름을 바꾸지 않는다. 루트의 인사·월계 지침과
매출 진입점도 기존 경로를 유지하며 목차에서 연결한다.

## 지침 유무와 판단 기준

- 업무 시작 시 메인 목차와 관련 문서를 확인하여 적용할 지침의 유무를 판단한다.
  파일이 없거나 읽지 못한 경우와, 파일은 있으나 필요한 기준이 없는 경우를 구별한다.
- 지침이 있으면 실제 문서의 기준을 따른다. 채팅 기억을 문서보다 우선하지 않는다.
  사용자가 이번 요청에서 다른 기준을 명시하면 변경 범위를 확인하고 담당 지침에 반영한다.
- 지침이 없으면 `지침 미정`이라고 밝힌다. 기존 합의처럼 추정하지 않는다.
  요청 범위의 읽기 전용 조사와 근거 수집은 진행할 수 있으나, 계산 정의·귀속·제외·
  자동 수정·삭제 등 결과를 바꾸는 업무 기준은 제안하고 사용자와 합의한 뒤 적용한다.
- 여러 지침이 충돌하면 해당 문서와 충돌 항목을 제시한다. 임의로 유리한 규칙을 고르지 않는다.
- 합의된 새 기준은 담당 Markdown에 기록하고 목차에 연결한다.
  문서 작성·커밋·푸시·실제 구현 상태는 별도로 보고한다.
- 지침의 존재는 기능 구현이나 운영 정상의 증거가 아니다.
  실제 실행 가능 여부와 성공 증거는 해당 업무의 완료 조건으로 확인한다.

## 업무별 분리 기준

1. 하나의 문서는 하나의 업무 책임을 담당한다.
2. 생산·재고·레시피·품질·매출은 별도 기준을 유지한다.
   종합 보고는 통합 운영 조회 지침에서 연결하며 각 기준을 중복 정의하지 않는다.
3. 매출 수집은 남선·대영 등 출처별 지침을 따른다.
   매장별 차이는 매출 진입점이나 해당 업무 지침에 연결한다.
4. 시스템 담당은 프로그램 역할, 실행 장소는 운영 실행 기준,
   접속은 공통 접속, 장애 조사는 운영 기록·추적 지침을 기준으로 한다.
5. 한 문서의 독립 업무가 커지면 별도 파일로 분리한다.
   분리할 때 원문을 확인하고 기존 링크·섹션 참조를 갱신한다.
   원문을 읽지 않고 제목만 보고 내용을 이동하거나 요약하지 않는다.

## 실행 가능한 업무 지침의 필수 내용

- 적용 요청과 범위, 담당 프로젝트와 관련 지침.
- 실제 원본 위치와 조회 경로, 권한·환경 준비 방법.
- 입력할 매장·날짜·상품·출처와 처리 순서.
- 현재 구현된 명령/API와 미구현 기능의 구별.
- 실패·누락·오래된 자료의 처리와 추가 확인 사항.
- 성공 증거·완료 조건·결과 저장 위치·사용자 보고 형식.
- 수정·삭제·푸시·배포 등 별도 요청이 필요한 행동.

자료가 부족하면 확보된 근거와 미확인 범위를 분리한다.
명령이 없는 절차에 가상의 CLI/API를 만들지 않는다.
자동화가 미구현이어도 수동·에이전트 절차가 있으면 그 절차를 안내한다.

## 변경과 검증

1. 해당 업무 지침과 연결 문서를 읽고 기존 규칙의 담당 파일을 확인한다.
2. 사용자 요청 범위만 수정한다. 새 규칙은 담당 파일 한 곳에 작성한다.
3. `WATERBE_GUIDE.md`에 연결하고, 필요한 경우에만 `AGENTS.md`에 직접 연결한다.
4. 기존 상대 링크의 대상과 섹션 참조를 확인하고 `git diff --check`를 실행한다.
5. 기획·코드 구현·테스트·배포·현장 확인을 각각 구분해 보고한다.
6. 기존 업무 기록과 다른 작업의 변경은 보존한다. 커밋·푸시·배포는 요청에 따른다.

## Git 관리 기준

- 지침・목차・기획・프로그램・검증 테스트는 해당 프로젝트 Git으로 변경 이력을 관리한다.
  비밀 설정, 실제 운영 DB, 대용량 원본 사진과 실행 로그는 무조건 Git에 넣지 않는다.
  원본은 담당 저장소에 보존하고 지침·점검 기록에는 식별자와 위치를 연결한다.
- 작업 시작 시 `git status --short`, 현재 브랜치와 원격을 확인한다.
  기존 수정과 이번 작업을 구별한다. 다른 세션의 미완료 변경을 덮어쓰지 않는다.
- 한 커밋에는 하나의 목적만 담는다. 문서 분리 시 본문과 목차·링크 갱신은 같은 커밋에 담는다.
  다른 기능 수정·운영 기록·배포 변경을 편의상 함께 묶지 않는다.
- 커밋 전 대상 diff, 새 파일, 비밀 포함 여부, 링크와 필요한 테스트를 확인한다.
  파일 단위가 섞였으면 변경 구간을 선택한다. 확인 없이 `git add .`로 전부 포함하지 않는다.
- 커밋 메시지는 `docs: 품질점검 실행 절차 정리`처럼 목적을 명시한다.
  의미가 바뀐 규칙은 변경 이유와 검증 결과도 커밋 본문 또는 관련 기록에 남긴다.
- 푸시 요청 시 원격 변경을 확인하고 충돌이 있으면 내용을 대조한다.
  강제 푸시·하드 리셋으로 다른 작업을 없애지 않는다.
  푸시 성공과 원격 커밋 일치를 확인한 뒤 완료로 보고한다.
- Windows와 씽크패드는 커밋 ID로 동일 버전 여부를 확인한다.
  작업 중인 변경 위에 자동으로 덮어쓰거나, 실행 중인 워커를 단순 Git 갱신만으로
  최신 배포라고 판단하지 않는다. 실행본 적용·검증은 해당 운영 지침을 따른다.
- 되돌리기가 요청되면 공유 이력을 보존하는 `git revert`를 우선 검토한다.
  Git은 운영 DB·원본 파일의 백업을 대체하지 않는다.
- 결과 보고에 변경 범위, 검증, 커밋 ID, 푸시 여부, 배포 여부를 구별해 적는다.
  커밋·푸시·배포는 각각 사용자 요청 범위에 따라 실행한다.

이 문서는 정리 방식의 기준이며 개별 업무 지침의 판정 기준을 대체하지 않는다.
