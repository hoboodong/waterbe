# 워터비 통합 운영 조회 기획안

작성일: 2026-09-26 · 상태: 제안 / 미구현

프로그램 전체 목록과 담당 경계는 [프로그램 구성·역할 지침](../guides/PROGRAM_RESPONSIBILITIES_GUIDE.md)을 기준으로 한다. 이 기획안은 그중 통합 운영 조회 개발을 구체화한다.

담당별 구체적인 범위·산출물·인수조건은 [통합 운영 프로그램 작업 지시서](INTEGRATED_OPERATIONS_WORK_ORDERS.md)를 따른다. 작업 지시서는 실행 승인 전 초안이며 작성만으로 구현·배포를 시작하지 않는다.

이 문서는 개발 범위와 프로젝트 간 책임을 정하는 기획안이다. 프로그램 실행, DB 변경, 저울 작업, 서비스 배포를 승인하거나 이미 완료했다고 뜻하지 않는다. 기존 운영 지침은 그대로 유효하다.

## 1. 목표

이전 대화를 모르는 새 코덱스도 `왕십리 오늘 생산량`, `월계 어제 할인까지`, `생산이랑 실제 매출 비교`를 같은 조회 프로그램으로 처리한다. 매번 SSH·DB 경로를 탐색하거나 계산식을 다시 만들지 않는다.

성공 기준은 '답변이 나온다'가 아니라 다음 네 가지다.

- 같은 원본 버전·기준시각·현장정보·계산 버전이면 같은 수치가 나온다.
- 전체 품목이 상품명·수량·중량·금액과 연결되고 합계를 검산할 수 있다.
- 조회 실패, 자료 지연, 일자 귀속 불명확을 0이나 계획량으로 채우지 않는다.
- 원본, 계산 근거, 미확정 이유를 추적할 수 있고 휴대폰에서 바로 바로잡을 수 있다.

## 2. 소유권과 책임

### 워터비: 사업 운영과 통합 조회의 주관 프로젝트

- 통합 조회 명령, 사업일·매장 해석, 사업 계산, 결과 형식, 최종 통합 검증을 소유한다.
- 생산·할인·폐기·전환·실제 매출을 연결한다. 생산금액과 실제 매출을 구별한다.
- 대영·남선 매출 가져오기·검증은 기존 워터비 프로그램의 책임으로 유지한다.
- 현장 신고, 원물 환산기준, 상품의 사업상 묶음, 레시피·원가·재고·입고·직원 정보의 업무 규칙을 소유한다.
- 저울 접속·프로토콜·초기화 해석을 복제하지 않는다. 시코드 원본을 임의로 수정하지 않는다.

### 카스씨엘(cascl5200): 장비 데이터의 수집·검증·제공

- 매장 접속·인증, CASPi/저울 통신, 원본 수집·보존, 누계 증가분과 초기화 검증을 소유한다.
- 지정 기간의 관측값, 직전 기준선, 수집 공백, 자료시각을 표준 읽기 전용 인터페이스로 제공한다.
- 중앙 수집·게시와 실패 진단은 카스씨엘 책임이다. 워터비 요청마다 새 수집기를 띄우지 않는다.
- PLU 수정·백업·검증 등 기존 쓰기 경로는 유지하되 이번 조회 프로그램과 분리한다.
- 결과는 '저울 관측값'이다. 최종 생산량·폐기·실제 매출이라는 사업적 판단은 하지 않는다.

### 시코드(seacode_new): 현장 앱과 상품·출력 이벤트

- 매장 운영상품·앱 가격, 할인 입력·출력·취소 상태, 사용자 조작과 화면을 소유한다.
- 상품↔PLU의 실제 연결은 기존 `product_scale_sync_bindings`를 제공한다. 워터비는 이를 조회하는 소비자다.
- 시코드가 생성하는 데이터의 조회용 뷰·스키마·권한 계약을 관리한다.
- 출력 사실을 부착·판매 사실로 바꾸지 않는다. 사업 종합 계산을 앱 안에 별도로 복제하지 않는다.
- 기존 앱 생산 입력이 있으면 시코드는 입력 원본을 제공하고 워터비가 통합한다. 앱 `actual_qty`와 `waste_qty`는 현장 신고 출처이며 `expected_qty`로 대체하지 않는다. 이 기획으로 시코드 기능을 삭제하거나 새 계획 시스템을 도입하지 않는다.
- 나중에 시코드에 종합 실적 화면을 넣을 때도 워터비의 같은 계산 결과를 소비한다.

### 겹치는 영역의 단일 책임

| 영역 | 원본/변경 책임 | 워터비의 역할 |
| --- | --- | --- |
| 앱 운영상품·앱 가격 | 시코드 | 조회·사업 상품과 연결 |
| PLU 실제 값·누계·수집 품질 | 카스씨엘 | 검증된 관측값 소비 |
| 앱 상품↔PLU binding | 시코드의 기존 연결 기능 | 연결 상태·유효시각 검증, 임의 생성 금지 |
| 여러 포장규격의 사업상 합산·원물 환산 | 워터비 | 근거·유효기간을 갖는 별도 규칙 관리 |
| 할인 출력·취소 | 시코드 | 현장 부착 확인과 결합·중복 방지 |
| 현장 신고·부착 확인·폐기·전환 | 앱 입력은 시코드, 대화 입력은 워터비 | 출처별 기록을 통합하고 같은 신고의 중복 반영 방지 |
| 실제 매출·공급업체별 수수료 기준 | 워터비 | 기존 검증자료 조회·비교 |

Supabase는 저장·교환 장소이지 업무 소유자가 아니다. 씽크패드는 실행 장소이지 별도 사업 프로젝트가 아니다. 공용 DB라는 이유로 다른 프로젝트의 테이블을 직접 변경하지 않는다.

## 3. 실행 구조

```text
질문 / 향후 앱 요청
  → 워터비 통합 조회 명령
      ├─ 카스씨엘 표준 조회 → 중앙 보관소 / 허용된 원본 내보내기
      ├─ 시코드 읽기 계약 → 상품·연결·할인 원본
      ├─ 워터비 검증 매출 → 남선·대영
      └─ 워터비 날짜별 현장정보
  → 검증·사업 계산 → 구조화 결과 → 모바일 문장
```

- 1차는 상시 통합 워커가 아닌 요청형 조회 명령으로 만든다. 기존 수집 워커를 재사용한다.
- 워터비는 카스씨엘의 버전 있는 실행 명령 또는 인터페이스만 호출한다. 다른 저장소 내부 Python 파일을 임의 경로로 import하지 않는다.
- 중앙 데이터가 없거나 오래됐을 때의 대체 조회는 카스씨엘 어댑터가 담당한다. 워터비 에이전트가 임의 계정·비밀번호·SSH 옵션으로 재시도하지 않는다.
- CASPi는 Supabase 자격증명을 가지지 않는 기존 경계를 유지한다. 중앙 게시와 실제 저울 수집의 위치는 기존 아키텍처에 따른다.
- 호스트별 실행파일·DB·자격증명 참조는 배포 설정으로 관리한다. Windows 경로를 Linux에 하드코딩하지 않는다.
- 조회와 새 데이터 동기화는 별도 명령이다. 조회 중 Drive 파일 이동·삭제, OCR 재적재, 저울 설정 변경, 서비스 재시작을 하지 않는다.

제안 명령 예시(아직 존재하지 않음):

```text
waterbe report --store wangsimni --date 2026-09-25 --include production --format mobile
waterbe report --store wolgye --date 2026-09-25 --include production,discounts,sales --format json
waterbe doctor --store wangsimni
```

`doctor`는 경로·읽기 권한·계약 버전·최근 자료시각만 점검한다. 설치·업데이트·재시작을 자동 실행하지 않는다. '오늘'은 요청 접수 당시 한국 날짜로 한 번 고정한다. 자정 뒤에 끝나도 대상일을 바꾸지 않는다.

## 4. 공통 데이터 계약 v1 제안

세 프로젝트가 같은 샘플과 스키마 테스트를 통과한 뒤 구현한다. 아래는 새 내부 계약의 제안 필드이며 현재 DB 컬럼이 모두 존재한다는 뜻이 아니다.

### 요청과 공통 응답

- 요청: `request_id`, 인증된 호출자, `store_id`, `business_date`, `timezone=Asia/Seoul`, `as_of`, 요청 항목.
- 기간: 해당 한국 날짜의 `[00:00, 다음 날 00:00)`을 UTC로 변환한다. 오늘은 `as_of`까지만 소비한다.
- 응답: `schema_version`, `calculation_version`, `generated_at`, 매장·기간, 품목, 합계, 출처별 상태, 경고, 사용자 확인 항목.
- 출처별 `queried_at`, `captured_at` 또는 `published_at`, `source_revision/record_ids`, `coverage`, 오류 코드를 보존한다. 조회시각을 수집시각으로 대신하지 않는다.
- 상태를 분리한다: 접근 결과(`ok/error/not_requested`), 최신성(`current/stale/unknown`), 범위 충족(`complete/partial/unknown`), 값의 근거(`observed/reported/estimated/unconfirmed`).
- 실패/불명 값은 null이다. 정상 조회에서 관측된 0과 구분한다. 부분 집계는 확인 범위의 소계와 미확인 범위를 함께 반환한다.
- 상품별 단위와 가격 기준(`per_item/per_100g/...`)을 명시한다. 원화는 정수 또는 명시된 반올림 규칙, 중량은 고정 단위의 정수/십진수로 계산한다.

### 카스씨엘 제공 계약

- 매장·부서·PLU, 저울 상품코드, 상품 스냅샷 시각, 원시 카운터와 검증된 구간 증가분.
- 전체 수량·라벨 장수·중량·금액은 별도 필드. 한 장=한 개를 무조건 가정하지 않는다.
- 각 구간의 시작/종료 회차 ID와 시각, 초기화·0 기준선·실패 회차·연결 공백 정보를 제공한다.
- 중앙에는 성공 회차만 내보내는 기존 경로가 있으므로, 중앙 자료로 확인한 공백과 Pi 실패 로그로 확인한 원인은 구분한다. 실패 이력이 없으면 원인을 추측하지 않는다.
- 저장된 증가분의 선행 회차 연결을 검증한다. A→C 수집 뒤 B가 늦게 삽입된 경우 A→B와 A→C를 중복 합산하지 않도록 카스씨엘 내부에서 정렬된 원본으로 재계산하거나 일관성 오류를 반환한다.
- Supabase 게시기는 회차 헤더·원본·증가분을 나눠 올린다. 헤더만 존재하는 회차는 완료가 아니다. 클라우드 조회를 사용하려면 카스씨엘이 회차별 행 수·관계·게시 완료를 보증하는 읽기 경계를 먼저 제공해야 한다. 초기에는 검증된 중앙 SQLite의 읽기 전용 트랜잭션을 우선 검토한다.
- 당일 첫 회차뿐 아니라 시작일 직전 기준선과 종료 경계 판정 근거를 제공한다. 날짜를 가로지르는 증가분을 당일분으로 자동 배분하지 않는다.
- 공백은 카운터가 계속 유지되어 총증가분을 알 수 있는 경우와, 초기화/날짜 경계 때문에 복원 불가인 경우를 구별한다. 00~01시 수집 부재만으로 자동 실패 처리하지도, 영업 전이니 무조건 0으로 보지도 않는다.
- 정상 0개 PLU 회차와 조회 실패를 구별한다. 초기화 감지 자체만으로 영업일 완전성을 보장하지 않는다.
- 작업용 PLU 제외 후보·근거·설정 버전도 제공하고 원본 관측값은 보존한다. 용도가 바뀐 코드에 옛 제외 규칙을 무조건 적용하지 않는다.
- 원시 중량·금액의 단위/배율은 계약 확정 전에 카스씨엘이 검증한다. 워터비가 원시 정수만 보고 kg·원으로 추정하지 않는다.

### 시코드 제공 계약

- 상품 ID·매장·이름·마트코드·가격·운영상태와 업데이트 시각, binding의 상태·해제(tombstone)·검증시각.
- 과거 조회에는 가능한 당시 연결·가격을 사용한다. 현재 비운영 상태만으로 과거 관측 품목을 제거하지 않는다.
- 할인 이벤트 ID·상품/코드·출력시각·수정시각·원가가 아닌 정상 판매가격·최종가격·할인율·라벨 수·취소 여부·단계·바코드·계약 버전.
- 인쇄 작업 한 행과 라벨 장수를 구분한다. 구형 이벤트의 수량 컬럼은 의미가 검증된 호환 어댑터로만 해석하고 미상은 미상으로 남긴다.
- 앱 오프라인 후 늦게 업로드한 이벤트와 나중 취소/복원을 반영한다. `printed_at`만 증분 조회 기준으로 사용하지 않는다. 초기 구현은 대상일 전체를 안정된 정렬로 재조회하고 페이지 완결·수정 충돌을 검증한다.
- 원본 출력 생성은 append-only 취지지만 `is_void` 등 상태는 바뀔 수 있다. 이벤트 전체가 영원히 불변이라고 가정하지 않는다.
- `is_void`는 N장 출력 작업 한 행 전체의 취소/복원이다. 일부 장수만 취소됐다고 임의 해석하지 않는다. 구형 NULL 값의 의미는 계약 점검 후 결정한다.
- `discount_stage=1/2`는 스캔 세션 모드이고 개별 물건의 라벨 계보가 아니다. parent/root 라벨 ID가 없는 현재 자료에서 단계·바코드만으로 재할인을 확정하지 않는다.
- `updated_at`이 클라이언트 시각이면 이것만으로 지연 업로드까지 잡는 전역 변경 커서가 되지 않는다. 장기 증분 동기화는 서버 수신시각/변경 커서의 실제 제공 여부를 확인한 뒤 설계한다.
- 체크인된 할인 뷰와 원본 테이블의 `discount_stage` 노출 여부가 다를 수 있다. 운영 스키마를 읽기 전용으로 점검하고 뷰 보완 또는 원본 어댑터 중 하나를 시코드 담당으로 확정한다.
- 상품명 추정 연결은 확정 연결로 쓰지 않는다. 미연결 PLU는 식별자·저울 이름·해당 금액을 별도로 보여주고 누락하지 않는다.
- 기존 binding에 과거 유효기간 이력이 없다면 현재 연결을 과거일에 확정 소급하지 않는다. 수집 당시 스냅샷을 보존하는 방안을 검토하고 그 이전 날짜는 이력 부재를 표시한다.

### 워터비 현장정보와 매출

- 현장정보: 날짜·상품·입력값·단위·발화/메시지 출처·추가/현재총량/정정 구분·확인시각·대체한 기록 ID.
- 보정은 원본 삭제가 아닌 별도 근거다. 라벨 1장에 수량 7, 재가공, 500g 별도 PLU 합산 등을 범위가 명시된 보정으로 적용한다.
- 부착 확인은 출력 묶음/수량/날짜와 연결한다. 40% 사전 출력 지시를 다음 날이나 다른 매장에 자동 이월하지 않는다.
- 현장정보 기록 명령은 조회와 분리한다. 같은 메시지 재수신은 한 번만 반영하고 정정은 이전 값을 남긴다. 기존 YAML은 초기 저장소로 유지하되 동시 쓰기·원자 저장·ID 중복 검사부터 갖춘다.
- 앱 생산 입력과 대화 신고가 같은 실제 생산을 가리키는지 연결 근거를 보존한다. 두 출처에 나타났다는 이유로 합산하지 않으며 불명확하면 대조 대상이다.
- 실제 매출은 공급업체, 매장, 대상일, 자료 집계일, 원본 참조, 검증상태, 수수료·세금·행사팀 포함 범위를 제공한다.
- 오늘 자료 미게시와 0 매출을 구별한다. OCR 검토 대기는 확정액에 섞지 않는다. 조회 요청이 매출 동기화를 자동 실행하지 않는다.

## 5. 계산과 출력 규칙

계산 코드는 워터비 한 곳에서 테스트한다. 코덱스와 앱은 같은 구조화 결과를 소비하며 금액을 다시 계산하지 않는다.

1. 매장·날짜·요청 항목과 필요한 출처만 결정한다. 생산 질문에 불필요한 매출 조회 실패를 끌어오지 않는다.
2. 출처별 자료를 조회하고 버전·시각을 고정한다. 서로 다른 출처가 완전히 동시 스냅샷이라는 가정은 하지 않는다.
3. 상품·PLU·포장규격·기간을 연결한다. 미연결·예외상품도 별도 행에 남긴다.
4. 저울 관측값과 현장 신고를 대조한다. 신고량에 이후 저울 누계를 무조건 더하지 않는다. 불일치와 보정 근거를 남긴다.
5. 원물은 해당 날짜 유효한 박스/팩/포장/수율 기준으로 추정한다. 개수·투입팩·라벨 장수는 다른 단위로 유지한다.
6. 할인 출력·부착·사전 출력·취소를 구분하고 동일 상품의 재할인만 대체한다. 동일 가격 바코드는 개별 상품의 고유 ID가 아니다.
7. `조정 생산금액 = 생산금액 - 확인된 전환 중복액`, `할인후생산금액 = 조정 생산금액 - 당일 생산분 최종 부착 할인액`을 적용한다. 할인 귀속 불명확은 조건부/미확인으로 남긴다.
8. 폐기는 별도 표시하며 할인 중복 차감을 피한다. 매출과의 단순 차액을 재고·손실·이익으로 부르지 않는다.
9. 월계 대영은 해당 자료의 기준을 확인한 뒤 `차감 전 환산액 = 차감 후 금액 / 0.785`를 적용한다. 다른 매장에 자동 복사하지 않는다.
10. 전체 품목과 합계를 검산한다. 상위 5개만 보여주지 않는다. 부분 자료면 확정 총액 대신 확인 소계와 누락 범위를 앞에 둔다.

모바일 출력은 프로그램의 공통 렌더러에서 만든다. 품목별 이름·수량/라벨·중량·생산금액·적용 할인, 하단 합계와 확인사항으로 구성한다. 긴 목록은 메시지를 나누되 품목을 생략하지 않는다.

텔레그램 전송은 렌더링된 결과만 전달하도록 기존 전송 프로젝트의 연동부에서 처리한다. 터미널 진행 화면, SSH 로그, 계정 사용량을 사용자 메시지로 중계하지 않는다. 별도 전송 프로젝트 변경은 해당 프로젝트 확인과 승인 후 진행한다. 필요한 경우 짧은 진행 안내 한 번만 보낸다.

## 6. 안전·장애·운영

- 조회 계정은 필요한 데이터에만 읽기 권한을 갖도록 설계한다. 기존 service-role 키를 단말·대화·Git에 복제하지 않는다. 장비 자격증명은 카스씨엘 실행부에 둔다.
- 보고 권한은 전송 채널에서 확인한 호출자 정보로 검사한다. 사용자가 메시지에 적은 이름/매장만으로 권한을 부여하지 않는다. 기존 앱/텔레그램 권한과 생산·매출 열람 범위의 차이는 배포 전에 확정한다.
- 초기 시간 예산 제안: 전체 30초, 출처별 10초, 일시 오류 재시도 최대 1회(전체 예산 내). 인증 오류는 반복 비밀번호 시도 없이 종료한다. 수치는 실제 측정 후 조정한다.
- 한 출처 실패가 다른 정상 결과를 지우지 않는다. 영향을 받는 합계만 미확인 처리한다.
- `AUTH_FAILED`, `SOURCE_UNAVAILABLE`, `STALE_SOURCE`, `INCOMPLETE_BOUNDARY`, `SCHEMA_UNSUPPORTED`, `UNMAPPED_PRODUCT`, `AMBIGUOUS_DISCOUNT` 등을 사용자 문장과 운영 로그로 분리한다.
- 최근 결과 캐시를 보여주면 반드시 대상일·자료시각·캐시 여부를 표시한다. 새 조회 실패 후 캐시를 최신처럼 반환하지 않는다.
- 실행 로그에는 request ID·소요시간·출처 상태·계산 버전을 남기되 토큰/비밀번호/전체 민감 원본은 남기지 않는다. 원시 누계 DB는 Git에 넣지 않는다.
- 읽기 전용 조회 실패를 해결한다며 누계 초기화·저울 변경·재배포·수집 서비스 이중 실행을 하지 않는다.

## 7. 구현 순서와 프로젝트별 산출물

### 0단계: 계약과 배포 사전 점검

- 워터비 주관으로 요청/응답 스키마, 예제 데이터, 오류 의미와 소유권을 문서화한다.
- 카스씨엘은 씽크패드에서 각 매장 원본 접근 경로·읽기 권한·현재 수집 주체를 검증한다. PC별 데이터 위치를 명시하고 중복 수집기를 만들지 않는다.
- 중앙 SQLite가 Windows에만 있으면 카스씨엘 조회 실행부는 우선 그 소유 호스트에서 실행할 수 있다. 씽크패드의 워터비가 안정된 읽기 경계로 호출하도록 하고, 중앙 수집 자체의 Linux 이전은 별도 전환 계획으로 분리한다.
- 시코드는 실제 운영 테이블/뷰, binding, 구형 출력 수량·취소·단계 필드와 권한을 읽기 전용 점검한다.
- 완료 조건: 정상·인증 실패·부분 자료 샘플을 세 프로젝트가 동일하게 해석. 운영 경로가 미확정이면 해당 매장 배포 보류.

### 1단계: 월계 생산량 조회

2026-09-26 사용자 선택으로 첫 검증 대상을 왕십리에서 월계로 변경했다. 첫 실제 조회 사례는 월계 2026-09-26(KST)이며, 왕십리의 수집 공백 사례는 후속 회귀 검증 대상으로 유지한다.

- 카스씨엘: 기간/기준선/초기화/공백을 포함한 표준 누계 조회와 테스트.
- 시코드: 상품·PLU 연결 조회 계약과 검증 가능한 스냅샷.
- 워터비: 요청형 report/doctor, 생산 조회, 전체 품목 합계, JSON·모바일 출력, 출처 검증.
- 완료 조건: 이전 대화 없는 새 세션에서 `월계 오늘 생산량` 한 문장으로 실행. 월계 현재 실측과 고정 샘플의 결과를 대조하고 정상/부분/실패 상태가 구분됨.

### 2단계: 월계 할인·현장정보

- 시코드: 할인 계약의 라벨 수·취소·단계·수정 반영을 보완하되 필요한 DB 변경은 별도 검토.
- 워터비: 현장정보 입력/정정의 중복 방지, 원물 환산, 전환·폐기, 최종 부착 할인 계산.
- 완료 조건: 여러 할인 단계·40% 사전 출력·반품 재부착·포장단위 변경 등 회귀 테스트 통과. 모호한 할인 연결은 확정되지 않음.

### 3단계: 실제 매출과 4개 매장

- 워터비: 기존 남선/대영 검증자료를 소비하는 읽기 어댑터와 동일 범위 비교.
- 카스씨엘/시코드: 마포·미아 포함 매장별 연결/권한/최신성 검증.
- 완료 조건: 네 매장에서 생산·할인·매출의 사용 가능 범위가 각각 표시됨. 장애 매장을 0으로 집계하지 않음. 실제 데이터가 없는 기능은 완료 처리하지 않음.

### 4단계: 확장(후속 범위)

- 워터비의 기존 레시피·원가·재고·입고와 연결해 원가/판매 기여 분석을 확장한다. 기존 요일별 계획표는 복원하지 않는다.
- 필요해질 때 워터비 결과를 캐시·정기 요약하는 워커와 시코드 실적 화면을 추가한다. 계산 함수는 조회 명령과 공유한다.
- 자동 발주, 인력 변경, 가격 변경, 저울 쓰기는 이 기획의 자동 실행 대상이 아니다.

| 같은 샘플 Windows/Linux 실행 | 숫자·경고 일치, 원본 DB와 저울에 쓰기 없음 |

## 9. 배포와 완료 판정

- 초기 실행 호스트는 씽크패드로 제안한다. 세 프로젝트는 각각 버전을 고정하고 호환 계약 버전을 확인한다.
- 배포 전 고정 샘플 테스트 → 읽기 전용 실제 대조 → 새 세션 질문 → 모바일 결과 확인 순으로 진행한다.
- 첫 출시에는 기존 수집 서비스와 저울 쓰기를 바꾸지 않는다. 새 조회 실행부만 배포하고 실패 시 이전 실행부로 되돌린다.
- '파일 푸시', 'CLI 버전 업데이트', '지침 반영'만으로 완료라고 하지 않는다. 실제 원본 접근과 품목 연결·계산·전달까지 증거를 남긴다.
- 현재는 기획안만 작성한 상태다. 아직 통합 조회 명령·워커·새 DB/RPC·자동 배포는 만들지 않았다.

## 10. 구현 전 확정할 항목과 근거

기획 기본안은 워터비 주관, 카스씨엘 수집/기간조회, 시코드 상품/할인 계약, 씽크패드 실행, 요청형 우선이다. 다음은 구현 전 확인 사항이다.

- 실제 중앙 누계 DB와 게시 경로 중 씽크패드가 안정적으로 읽을 기준 경로. 문서상의 경로만 보고 운영 중으로 간주하지 않는다.
- 현재 스키마에서 할인 단계·구형 라벨 수·수정시각·binding 이력의 가용 범위. 없는 과거 이력은 만들어내지 않는다.
- 생산·매출 조회의 사용자별 허용 매장과 기존 텔레그램 전송부의 연동 방식.
- 최신성 임계값·시간 제한은 현재 수집/업로드 주기를 측정해 확정한다.
- 시코드 README의 과거 `Waterbe YAML → 전체 상품` 도식과 현행 운영상품 원본 지침이 충돌한다. 현행 매장 운영상품은 시코드 기준으로 설계하며 구현 단계에서 관계 프로젝트 문서를 함께 정리한다. 이번 기획으로 상품 소유권을 자동 이전하지 않는다.
