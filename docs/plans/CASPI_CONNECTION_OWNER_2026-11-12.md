## 담당과 구조

```text
기존 앱 Bluetooth ─┐
중앙의 기존 명령 ──┼─ 기존 CASPi 접수·작업 ID·영수증
자동 관측·누계 ────┘          ↓
                       공통 작업 순서 관리
                              ↓
                     저울 연결 담당 하나
                              ↓
                           CL-5200
```

- 연결 소유자는 CASPi 기존 서비스 안에 둔다. 별도 매장별 워커나 두 번째 상시 서비스는 만들지 않는다.
- subprocess/SSH CLI도 소켓을 직접 만들지 않고 서비스 내부 실행기에 권한 제한된 로컬 IPC로 요청한다. 서비스 내부 호출은 같은 실행기를 직접 사용한다. IPC는 길이 제한·요청 검증·호출자 권한·시간 제한을 갖는다.
- 상품/광고/성분/누계/관측/백업의 모든 정상 운영 저울 접근을 수렴시킨다. 모듈별 전역 소켓 캐시는 프로세스 간 공유가 아니므로 해결책으로 삼지 않는다.
- 연결은 한 곳이 읽고 쓴다. 동시에 송신 중인 명령은 하나이며, 응답 전체를 해석한 뒤 다음 명령을 보낸다. EOF 감시 스레드가 응답을 따로 소비하면 안 된다.
- 공통 `/run/lock/caspi-scale.lock`을 연결 소유 기간 유지한다. 내부 작업의 중첩 flock은 제거할 수 있도록 소유권을 전달한다. 기존 외부 도구는 계속 같은 잠금을 따른다.
- 네트워크 설정/복구는 connectivity 담당, 명령·검증·영수증은 scale-data 담당. CASPi가 수파에 직접 접근하거나 인증을 보유하지 않는다.

## 연결 상태와 시간 정책

연결 상태: 미연결 → 연결 중 → 사용 가능 ↔ 명령 처리 중 → 정상 종료 또는 연결 불확실.
작업 상태와 연결 상태를 분리한다. 연결 복구가 미확정 쓰기의 완료를 뜻하지 않는다.

- 연속 작업은 같은 연결로 바로 실행한다. 매 요청 전20초 sleep, 일정 시간마다 강제 재접속, 연결 유지를 위한 불필요한 PLU 읽기를 넣지 않는다.
- 유휴 중에는 소켓 읽기 가능/오류 이벤트를 관측한다. EOF/RST면 소켓을 정리하고 다음 실제 요청에서 연결한다. 처리 중에는 동일 수신기가 프레임/EOF를 판단한다.
- EOF 미관측은 생존 보장이 아니다. 다음 송수신 실패도 처리하며, 갑작스러운 전원 차단은 정상 FIN처럼 즉시 알 수 없음을 전제로 한다.
- connect/첫 응답/프레임 사이 무응답/작업 전체에 각각 유한 deadline을 둔다. monotonic 시간을 사용하고, 전체 읽기를 단일 읽기와 같은 총시간으로 제한하지 않는다.
- 정상 요청에는 인위적 대기가 없다. 장애가 지속될 때는 한 연결 시도만 허용하고 제한된 재시도 간격과 회로 차단으로 폭주를 막는다. 고장 난 장비에 대기 없이 무한 접속하는 것은 금지한다.
- 기존 timeout 값을 출발점으로 쓰고 장비별 실측 후 조정한다. 시험의3초·20초를 제조사 규격으로 고정하지 않는다. 끊김 없는 즉시 복구를 보장한다고 설명하지 않는다.
- 실패 감지 직후 다음 작업이 즉시 새 연결을 시도할 수 있으나, 장비 내부 이전 세션 잔류로 접속을 거부하면 실제 연결 가능 여부로 복구를 판정한다. RST/강제 close로 이를 해결한다고 가정하지 않는다.

## 상황별 처리

| 상황 | 처리·완료 기준 |
| --- | --- |
| 첫 실행/연결 없음 | 실제 요청 시 한 번 연결. 깨우기용 임의 명령 없음 |
| 상품 한 개/문구 한 개 조회 | 현재 연결로 명령1개, 대상·길이·BCC 확인 |
| 전체 PLU 조회 | 같은 연결에 순차 명령. 완료/실패 번호와 시작·종료 시각을 보존. 부분 성공을 전체 성공이나 삭제로 해석하지 않음 |
| 전체 읽기 도중 현장 요청 | 완전한 응답 경계에서 양보. 소켓은 유지. 조회와 쓰기를 병렬 송신하지 않음 |
| 누계 수집 도중 요청 | 기존 수집 일관성 계약 유지. 안전하게 중단 가능한 경계만 양보하고, 이어 읽기 불가한 프로토콜은 별도 수집 회차로 다시 읽음. 다른 회차 누계 조각을 합쳐 성공 처리하지 않음 |
| 자동 조회가 몰림 | 동일 대상/동일 신선도 조건 읽기는 합침. 쓰기 전후를 가로질러 합치지 않음. 자동 작업은 상한이 있는 큐에 유지 |
| 여러 폰/중앙 동시 요청 | 같은 실행 큐와 불변 작업 ID로 직렬 처리. 현장 우선, 대기시간 가중으로 배경 작업 기아 방지 |
| 진행 중 쓰기 | 사전 읽기→기대값 검사→증거 보존→쓰기→ACK→재읽기 전체를 끊을 수 없는 작업 구간으로 처리. 검증 도중 다른 명령 삽입 금지 |
| 유휴 후 정상 EOF | 고장 알림 없이 미연결로 전환. 새 작업 때 재접속 |
| 케이블 단절/전원 꺼짐/응답 정지 | 유한 timeout으로 종료. 연결 담당만 복구 시도. 화면/다른 매장/기록 전달은 계속 |
| 연결 확인 직후 단절 | 사전 생존 확인만 믿지 않고 실제 송수신 실패 처리. '연결됨'만으로 쓰기 성공 판정 금지 |
| 읽기 중 일부 프레임/잘못된 BCC/다른 대상 | 결과 게시 금지, 해당 연결을 불확실로 폐기. 한정된 읽기 재시도 가능 |
| 지연 응답/중복 ACK/남은 바이트 | 응답 종류·대상·길이·종료 규칙 검사. 예상 밖 데이터는 다음 요청 응답으로 사용하지 않음. 세션 세대를 새로 부여 |
| 쓰기 전 접속 실패 | 저울로 전송하지 않았다는 증거가 있을 때만 안전한 재접속 경로 허용 |
| sendall 예외/일부 쓰기 송신 | 미적용이라고 단정하지 않음. 전송 가능성만 있어도 재쓰기 금지, 원 작업 읽기 재확인 |
| ACK 유실/ACK 후 재읽기 실패 | 원 작업과 대상만 미확정 보존. 재접속 후 읽기로 확인. 누락 ACK를 만들어 성공 처리하지 않음 |
| 광고·성분 여러 프레임 중 단절 | 일부 적용 가능성을 보존하고 원문 전체 재확인. 중간 프레임부터 또는 처음부터 자동 재전송 금지 |
| 요청 내용과 다른 값/잘림 확인 | 구체적 실제값으로 확인 필요 표시. 연결 복구로 보류를 자동 해제하지 않음 |
| 같은 ID 중복 도착/BT 뒤 중앙 재전달 | 접수 내용 해시 같으면 기존 진행/영수증 반환, 다르면 거절. 경로 변경으로 새 작업 생성 금지 |
| 폰 BT만 끊김/앱 종료 | 이미 내구성 있게 접수한 작업은 파이가 완료·기록. 폰 재접속 시 같은 ID 결과 반환. 폰 단절을 저울 실패로 표시하지 않음 |
| 인터넷/중앙/수파만 장애 | BT 현장 실행 유지, 영수증 전달만 별도 보류. 복구 후 동일 사건 ID로 전달 |
| 직원이 저울에서 직접 수정 | 실행 직전 기대값 비교. 불일치면 최신값과 차이 반환. 사용자 승인 없이 현장값 덮어쓰기 금지. 저울에 원자적 비교쓰기 기능이 검증되지 않았으므로 경쟁 가능성은 재읽기로 확인 |
| 요청 취소 | 실행 전만 안전 취소. 쓰기 시작 후 취소/클라이언트 timeout은 작업 삭제가 아니라 결과 확인으로 전환 |
| 파이 재부팅/프로세스 종료 | OS 잠금 해제와 새 세션 시작. 원장 미완료 쓰기를 먼저 읽기 재확인. 이전 running을 무조건 재실행하지 않음 |
| 파이 디스크/DB 오류 | 내구성 있는 접수·쓰기 전 증거 저장 실패면 쓰기 송신 금지. 메모리에만 접수하고 성공 응답 금지. 저장이 필요 없는 진단 읽기는 별도 구분 |
| 대상 하나 미확정 | 해당 PLU/문구만 보류. 그 문구를 새로 참조하는 의존 작업은 보류, 무관한 상품 조회·작업은 계속 |
| 새 릴리스/원복 | 신규 접수 인계, 진행 중 쓰기 보호, 원장 보존. 이전 프로세스 종료·잠금 획득 확인 전 새 소유자 실행 금지. 미확정 쓰기는 버전 변경 후에도 유지 |
| 다른 프로그램이 저울 직접 접속 | Pi 밖 CL Works 등의 연결은 공통 잠금으로 막을 수 없음. 외부 연결 가능성을 기록하고 모든 거부를 CASPi 코드 오류로 단정하지 않음 |

## 구버전 호환과 V1 경계

- 앱 Bluetooth 명령, SSH CLI 명령, 작업 ID, 필수 응답/영수증 형식은 보존한다. 앱 업데이트를 배포 전제로 하지 않는다.
- 기존 CLI를 내부 IPC 클라이언트로 바꾸는 경우 오류 의미·종료 코드·timeout·JSON을 회귀 검증한다. 실행기 장애 시 CLI가 직접 소켓을 여는 자동 우회는 금지한다.
- V1 `20304` relay는 현재 flock+socat인 byte-transparent 경로다. 영구 연결 소유자가 잠금을 잡으면 기존 relay가 계속 대기할 수 있다. 이를 해결하지 않고 '기존처럼 사용 가능'이라고 보고하지 않는다.
- V1은 운영 예비 경로라는 기존 정책을 유지한다. 명시적인 사용 요청 시 새 V2 접수를 조정하고 진행 중 쓰기/미확정 작업을 확인한 뒤 연결 종료와 잠금 인계를 검증한다. V1 종료 후 소유권 회수도 검증한다.
- 이 인계는 매 명령20초 대기와 다르다. 실제 장비가 종료를 지연하면 전환 지연은 남을 수 있다. V1을 항상 즉시 병용해야 하는 요구는 별도 호환 설계/시험이 필요하다.
- 원시 바이트 relay를 검증 없이 기존 소켓에 붙이면 늦은 응답·다른 종류 응답이 섞일 수 있으므로 자동 연결 공유를 하지 않는다.

## 표시·기록·자원

- 기존 앱의 상태 필드는 유지하고 지원되는 설명 필드로 '다른 요청 처리 중', '저울 응답 없음', '변경 결과 다시 확인 필요', '저울 적용 확인·공유 전송 대기'를 구분한다. 구앱이 표시하지 못하는 설명은 중앙 기록으로 남기고 지원 범위를 명시한다.
- 자료에는 마지막 실제 읽기 시각을 유지한다. 과거 캐시를 방금 읽은 값으로 게시하지 않는다.
- 같은 작업 ID로 요청/전송 시작/ACK/재읽기/중앙 수신/앱 게시 증거를 연결한다. 소켓 세대·접속 횟수·대기/실행 시간은 진단 메타데이터다. 해시만으로 성공을 판정하지 않는다.
- 반복 정상 읽기마다 전체 payload를 영구 추가 저장하지 않는다. 최신값+변경 이력+미확정 작업 증거를 기존 보존/중앙 ACK 계약에 따라 관리한다. 한도 없는 큐·로그·프레임 버퍼를 만들지 않는다.
- 큐 포화는 접수 전 명확히 거절하거나 중복 읽기를 합친다. 접수 완료한 쓰기를 조용히 버리지 않는다. 중앙 단절이 길어 저장 상한에 도달하면 무손실·무한 가용성을 동시에 보장할 수 없으므로 기록 불가 쓰기를 안전하게 거절한다.
- 장애/복구는 실통신 증거 기반, 동일 사건 중복 억제. 서비스 active나 ping만으로 복구 알림을 만들지 않는다. 기존 Telegram 발신 정책을 유지한다.
- 감시 불가: Pi 자체 전원 단절, 직접 외부 프로그램 사용, 미등록 대상 변경, 폰 실제 수신은 각각 별도 관측 증거가 필요하다.

## 구현 순서와 통과 조건

1. 설치본 파일 해시/버전과 최신 원격·미커밋 보강 대조. 직접 TCP9600을 여는 모든 모듈·점검 도구·relay/누계 경로 목록 확정.
2. 기존 서비스 내 단일 소유자와 IPC/순서 관리 구현. 먼저 모의 저울로 EOF/RST/무응답/분할·지연·오염 응답/동시 요청/큐 상한 검증.
3. PLU·문구 읽기·관측·전체 조회·누계 통합. 유휴 EOF 후 첫 읽기, 긴 조회 중 현장 요청, 미완료 전체 결과 게시 방지, 누계 회차 일관성 검증.
4. 쓰기 전/중/후 단절과 프로세스 강제 종료를 모의환경 각 지점에서 시험. 같은 ID와 다른 경로로 재요청해도 쓰기가 중복되지 않아야 함. 서로 다른 ID의 충돌 작업도 검사.
5. PLU와 문구의 사전 확인/쓰기/재읽기를 같은 연결로 수행하도록 통합. ACK 종결 문자와 남은 바이트까지 정확히 소비하는지 검증. 누계 혼합도 실제 지원 여부를 따로 검증.
6. 구앱/새 CASPi, 기존 중앙 CLI, BT 단절 후 결과 재조회, V1 명시적 인계, 원복을 검증. 기존 보류는 임의 해제하지 않음.
7. 월계 읽기부터 제한 적용·장시간 관측 후 실제 쓰기는 지정 시험 대상 또는 사용자 요청 변경으로 검증. 운영 자료에 임의 no-op 쓰기/전원·케이블 장애 시험 금지.
8. 모든 매장에 동일 공통 릴리스를 적용하고 개별 연결/연속 읽기/유휴 종료/쓰기 증거를 구분해 확인. 시험값20초를 전 매장 강제하지 않음.

완료 기준: 한 매장 정상 운영 저울 연결 소유자1개, 요청 간 불필요한 신규 연결 제거, 응답 혼선0, 시험상 중복 쓰기0, 모든 요청이 유한시간에 결과 또는 구체적 확인 필요 상태, 장애 대상 외 작업 지속, 기록/메모리/큐 증가 상한, 구버전 계약 회귀 통과. 물리 고장이나 외부 프로그램 간섭까지 '장애가 절대 없음'으로 보장하지 않는다.

별개 남은 문제: 월계 광고2번 잘린 값과 기존 pending은 이 통신 개선만으로 해결되지 않는다. 원 작업 내용·실제값을 대조하는 문구 복구 절차가 필요하다.
